Forward deployed engineer

The loop grades whether you can own a customer outcome, not whether you can invert a tree.

An FDE writes production code on someone else’s infrastructure, in a problem that was underspecified on Monday and on fire by Thursday. Interviews follow the job: structure ambiguity out loud, get useful in a stack you have never seen, and defend a design a skeptical operator would actually use.

Signal 1

Decomposition

Vague prompt. No spec. You name the user, the number they are measured on, the hard part, and a thin slice — before any architecture diagram.

Signal 2

Useful by afternoon

Learning and re-engineering rounds drop you into unfamiliar docs or a buggy 200-line module. Trace one path. Hypothesize. Then touch code.

Signal 3

Production judgment

Evals, guardrails, cost, stale data, and “what if they ignore the recommendation.” Demo-shaped answers fail. Shipped-shaped answers pass.

Where hours should go. Keep a coding floor (hash maps, graphs, grouping messy events, SQL). Spend the real reps on timed decomposition out loud, a learning-round debug, and a “why this company” answer that could not be pasted onto a different employer. Silence is ungradable. Narrate.

How to use this kit

  1. Read the company loop you are actually walking into. Formats drift — confirm with the recruiter.
  2. Run one decomposition drill on a five-minute timer, out loud, then grade yourself against the five moves. Do not read the worked examples and call it practice.
  3. Clear the three coding problems until the tests go green without peeking.
  4. Do the Ledger learning task: read the docs, reproduce the bug, then fix it.
  5. Write the five behavioral stories into the cards. They persist locally.

Anthropic-style and startup FDE

Live coding is often practical and escalating: a simple version must survive the second and third requirement. Docs and search are frequently allowed. Values/mission rounds are failable. Startup loops compress the same signals into fewer hours: one coding session, one case, one founder conversation.

Four things graded in every room

  • Own the customer number, not the artifact.
  • Translate to cost, risk, and ROI without being asked.
  • Name what breaks in production before the interviewer does.
  • Commit to a position, name the tradeoff, update if the pushback is right.
Signature round

Decomposition

You are handed a vague, often non-software problem. The interviewer can only grade what you say. The mistake almost everyone makes is jumping to a product in the first minute.

Five moves — say them in this order

1
User and outcomeWho is in pain, and what number are they measured on? Not “an app.” A dispatcher’s time-to-dispatch. A nurse’s hours after shift.
2
Assumptions, out loud, then checkState what you are taking as true and what you are scoping out. Ask two or three questions that would change the design — not a questionnaire.
3
Sub-problems of the problemThree to five parts of the underlying problem, never phases of a build (ingest / model / dashboard is a build plan, not a decomposition).
4
The hard partThe sub-problem where a miss sinks the outcome. Safety, trust, adoption, a join that will not join. Defend why it is hard.
5
Thin slice + how you would know it is wrongOne concrete first version that is useful alone. Name the metric and the failure that would kill it. Then stop talking in hypotheticals.
If they say “you have been structuring a while — give me something concrete,” that is a test, not impatience. Commit: “Here is version one, and here is why the hard part drove it.”

Worked example

Prompt: a city wants to cut emergency dispatch times in half using “our platform.”

Bad

“I’d put a classifier on the 911 audio and a dashboard that auto-assigns the nearest unit.” You picked a model and a UI before you knew which interval they mean, who the user is, or whether the data joins. Every later decision now sits on a guess.

Good

You ask: call-answer to dispatch, or dispatch to on-scene? Who sits in the chair — call taker or dispatcher? What is the baseline, average or tail? Then you sketch CAD + GPS + a map. Real questions, still mostly designing a product. You have not named the failure that actually kills deployments: a recommendation nobody trusts, or a map that lies with stale GPS.

Great

The user is the dispatcher. The outcome is the right unit moving sooner, measured as dispatch interval by incident type — and misroutes must not rise. Sub-problems: understand the call, know unit state, choose a unit, recover when that unit is wrong or unavailable. The hard part is not the map; it is acting on dirty, late data without silently lying, because a stale location is worse than no location. Thin slice: two weeks, one district, live unit status plus an incident clock, staleness visible, no model. I would know it is working if dispatchers keep it open during a shift and interval starts moving before we touch routing. Optimization comes after the picture is trusted.

Timed drill

Five minutes. Out loud. Notes are optional; the grade is whether the five moves happened.

The brief

        
Ops says delayed-shipment counts in the morning report are roughly 2× reality after we turned on “replay catch-up” last week. The dashboard calls summarize(events, now). Fix it without breaking live (non-replay) events. Do not rewrite the module.


        
Ledger.md — what they handed you

        
Ledger is a tiny event fold used by dispatch.

Events:
  { id, status, ts, loc, kind? }
  status: PICKED_UP | IN_TRANSIT | DELAYED | DELIVERED
  kind:  (omit) live event
         "replay"  — a catch-up copy of an event the link dropped.
                     Same id + status + ts + loc as the original.

summarize(events, now) → {
  shipments: { [id]: { status, loc, ts } },   // latest live state per id
  delayed:   number                           // ids whose latest state is
                                              // DELAYED and (now - ts) >= 48h
}

Replays must not change counts or overwrite a newer live state.
Ignore unknown statuses.
Do not mutate the input array or its objects.


        
Starter is the customer’s current function. Tests encode the bug report plus the live-event cases that must keep working.

AI system design

        
Lead with how you would know it is correct and how you bound failure. Architecture comes after the eval. A model is a component, not a plan.

        

          
1
Golden set before the modelWho labels it, how big for v1 (often ~50–100), what a pass looks like, and which failures are launch-blocking vs. annoying.

          
2
Split the pipelineRetrieval quality vs generation quality vs tool success. One blended “accuracy” number hides the break.

          
3
Guardrails and data boundaryWhat the model must not say or do; where customer data lives; who can see traces.

          
4
Cost, latency, fallbackThe path when retrieval is empty, the vendor is down, or the user is the veteran who will never open a chatbot.

          
5
Week-one sliceShadow mode, one workflow, human in the loop. How you decide to take the training wheels off.

Values and hiring manager

        
Generic enthusiasm fails. Palantir’s own advice is to understand the business and to tell a real failure. Write specifics. These cards stay in localStorage.
